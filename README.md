# D10 - Space-Saving 網路流量告警實驗

軟體定義網路及網路功能虛擬化課程專題。使用 Space-Saving 在有限的計數器預算下，偵測累計封包數達到告警門檻的來源 IP。

## 研究問題

> What detection coverage and delay are traded for fewer false alerts when decisions use an estimate's lower bound?

在相同的封包串流、告警門檻和計數器預算下，比較兩種告警規則。用 Space-Saving 的估計次數下界觸發告警，能減少多少誤報？有多少真正達到門檻的來源會漏報，成功偵測的來源又會晚多少筆封包才被偵測到？

設告警門檻為 T、估計次數為 c、可能高估的上限為 e。分別比較 **估計值告警（c ≥ T）** 和 **下界告警（c − e ≥ T）**，用逐筆精確計數作為判定基準。對每組流量分布與門檻，可測試 16、32、64、128 個計數器。

## 共用介面與評估方式

- **輸入**：UTF-8 純文字，每行一個來源 IP，保留原始順序。三人先用同一個小樣本確認介面。
- **告警紀錄**：每處理一筆封包，就對該來源 IP 套用兩種規則，分別記錄首次告警序號。若某來源曾提早誤報，仍繼續評估規則，以記錄它達到門檻後首次符合告警條件的序號。
- **誤報**：計算有多少來源 IP 在真實次數達到門檻前就觸發告警，每種規則對同一來源最多計一次。始終未達門檻但曾告警的來源也計入。
- **偵測覆蓋率**：在真正達到門檻的來源中，計算從達標到觀察結束之間至少有一次符合告警條件的比例。若資料中沒有達標來源，標為不適用。
- **偵測延遲**：用達標後首次符合告警條件的封包序號減去精確達標序號，同一筆封包偵測到的延遲為 0。未偵測的來源另計為漏報。比較兩種規則的延遲差時，使用兩者都成功偵測的來源。

## 整合順序

1. **共同確認**：填上組員姓名，確認告警門檻、觀察範圍與第一批測試資料。
2. **並行開發**：A 提供更新程式與手算測試，B 提供資料和精確達標序號，C 先用小樣本完成批次實驗框架。
3. **整合驗證**：三人核對小樣本的誤差界、誤報、漏報和延遲，再執行完整參數組合並整理報告。
